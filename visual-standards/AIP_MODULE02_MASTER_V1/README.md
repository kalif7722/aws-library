# AIP Module 02 — Master Visual Standard V1

Status: **reference-based candidate; approval pending**. Source: 20 user-supplied AIP Module 02 screenshots (1116×627 each, 16:9), supplied 17 November 2026. These are reference previews, **not** original 2048×1152 master assets. Do not modify published course slides or claim that this represents every Module 02 slide.

## Design DNA

- **Canvas:** midnight/deep navy (#06162D to #0A2340 approximate); quiet, flat or lightly graded background. Minimal decoration. No mountains, pedestals, glowing theatrical scenery, giant logos, or arbitrary cloud illustrations.
- **Text hierarchy:** prominent white sans-serif all-caps topic titles with a meaningful **orange** emphasized phrase; concise but substantial white teaching premise beneath. Smaller white/cyan section headings, readable annotations, monospace for JSON/CLI/data.
- **Semantic colors:** white for primary text; orange (#FF982D) for emphasis/action/forward processing; cyan (#20D7DF) for structure/data/active flows; purple (#9A65F4) for models, identities or transformations; occasional blue/green for categories/validation. Colors serve meaning, not decoration.
- **Layout:** concept-driven. 16:9 canvas; ~2–4% edge padding; quiet background behind text. Small MODULE 02 marker top left and index top right on originals (replace with correct course/module markers in new content).
- **Panels:** slim 1–2px colored borders, restrained rounding, dark or transparent interiors. Moderate local glow on important symbols only, not thick glass frames. No gratuitous card grids.
- **Icons:** primarily crisp flat, outlined, recognizable pictograms; no fake official AWS branding. Use genuine official assets when exact service icon fidelity matters.
- **Arrows:** solid and unambiguous directional connectors. Orange for major stage transitions; cyan for data paths and technical routing; purple for specialty transformations. Arrow directions and boundaries must be technically correct.
- **Content density:** teach actual operation with diagrams, examples, accurate data, annotations, relevant caveats; 3–7 meaningful components, not sparse slogans. Preserve the entire specified claim and source coverage; split across slides rather than shrink text below legibility.
- **Bottom insight strip:** optional and only where it explains a misconception or important conclusion. Not mandatory on every slide.
- **Visual depth:** exceptionally restrained dimensional treatment compared to earlier glossy Security drafts. Match original AIP's 2D instructional vocabulary first; small shadow or gentle local bloom on service icons only.

## Layout taxonomy; choose by the teaching relationship

1. **Left-to-right flow / pipeline:** source → processing → output (images 01, 08, 09, 18, 19, 20).
2. **Source/contract/result:** schema, JSON, input/output mapping with exact field names (02, 03, 04, 07, 13).
3. **Before/after comparison:** original document/data vs improved structured version (05, 16).
4. **Transformation walkthrough:** genuine steps with illustrated intermediate results (06, 14, 15).
5. **Multi-modal or branching extraction:** visual input to outputs with one arrow per output type (10, 11, 12).
6. **Service architecture/data lineage:** service boundaries and sources/destinations (17, 19, 20).

The composer should choose the minimal diagram that faithfully expresses the **actual technical relationship**, not alternate layouts mechanically.

## Contrast with rejected draft slides

Reject excessive glossy/3D treatment, glowing neon outlines, thick decorative frames, pedestal icons, fake branding, oversized hero objects, heavy top bars, and universally imposed three/four card layouts. The actual AIP references are precise explanatory slides, not marketing infographics. In particular the rejected S3 and KMS previews should NOT be treated as references.

## Image requirements

- Final export: **2048×1152 WebP**, quality 94, one complete slide per file.
- Text-heavy material: compose labels, JSON snippets, code, and tables deterministically with a real font after AI illustration, not with image generation alone; exact field spellings and arrow direction are QA-critical.
- Inspect at full size AND at representative course viewport dimensions; fix errors before presenting.
- Preserve source completeness and technical correctness; citations/source anchors in the production manifest, not tiny text on the slide.
- Publication: **none until explicitly approved**. This branch is a design-only draft, not a live course update.

## Application scope

Use this visual language for future slides in Security, SAP, SAA, Developer Associate, AIF and other courses, without rewriting their content or overwriting approved existing visuals. Any preexisting course-specific approved style is a constraint to reconcile, not permission to replace it. This design standard is candidate until user review.
